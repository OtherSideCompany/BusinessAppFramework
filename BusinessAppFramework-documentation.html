OverviewREADME.md

Introduction#

BusinessAppFramework gives you the plumbing every back-office application needs, so that a business module only has to describe what it manages, not how it is stored, searched, displayed or exported.

Out of the box it provides:

  • Domain objects with identity, audit trail, references between objects and parent/child hierarchies.
  • Persistence on SQL Server or SQLite through Entity Framework Core, with a clean separation between domain objects and database entities.
  • Search with pagination, sorting and named constraints (filters) for every domain object type.
  • A generic REST API that exposes create / read / save / delete / search for any registered domain object.
  • A Blazor UI toolkit (MudBlazor) with ready-made browsers, editors, selectors, dialogs, KPIs and workspaces.
  • Workflows (steps, transitions, conditions) that drive the state of a business object.
  • Document generation: HTML templates rendered with Scriban and turned into PDF with a headless Chromium.
  • Cross-cutting services: authentication (JWT), module and user settings, localization, mail, file storage, image compression, logging.

An application built on the framework is the combination of framework libraries (this repository), one or more business modules that plug into them, and a host that wires everything together. This repository only contains the framework; it ships no executable.

Architecture at a glance#

The solution follows a clean architecture. Dependencies only point inward, towards the domain.

Bootstrapper sits above the layers: it does not belong to any of them and only exposes generic helpers. The host, which lives outside this repository, uses them to wire every module, pick a database context and start the web server.

The WebUI never talks to the Infrastructure layer directly. It calls the REST API exposed by the Adapter through small HTTP gateways, using the routes defined in Contracts.

Read more in the Architecture chapter.

Key concepts#

A few words you will meet everywhere in the code:

Domain object
A business entity handled by the framework (a customer, an order, a task…). It derives from DomainObject, which gives it an id and audit fields.
Module
A package of business features that registers its domain objects, services, UI descriptors, workflows and constraints through an IModuleBootstrapper.
Workspace
A screen of the application. A workspace descriptor says which Blazor component renders it. The most common one is the domain object browser, a searchable list of one domain object type.
Application action
A declarative description of something the user can trigger (create, delete, navigate, download, open a dialog). The UI renders it as a button, the backend executes it.
Constraint
A named filter applied to a search, exposed in the UI as a chip the user can toggle.
Relation
A typed link between domain objects. References point to one object, reference lists to many, parent/child relations build trees.
Workflow
An ordered set of steps with transitions and conditions that move a domain object through a business process.

Layers#

BusinessAppFramework follows the clean architecture principles: the business rules sit at the center, technical concerns sit at the edges, and every dependency points inward. A layer never knows about the layers outside it.

Three projects form the core and carry no technical dependency: Contracts, Domain and Application. The five others sit at the edges and depend on the core: Infrastructure, DocumentRendering, Adapter, Bootstrapper and WebUI. The diagram in the overview shows them side by side.

Contracts

Constants that every layer, frontend included, needs to agree on: action keys, constraint keys, error and message keys, settings keys, API route segments and a few enums. It depends on nothing. Keeping it apart from Domain means the Blazor frontend can build an API URL or display an error key without pulling in business types.

Domain

The heart of the model: the DomainObject base class, the DomainObjectReference and DomainObjectReferenceList types used to link objects together, LocalizedText for multilingual values, and a handful of marker interfaces (IIndexable, ISystemObject, IHasReferenceNumber). No persistence, no HTTP, no UI.

Application

The use cases and the ports. This is where the framework defines what it can do, as interfaces, and implements the parts that do not depend on a technology:

  • IDomainObjectService<T> and its default DomainObjectService<T>: the CRUD use cases for any domain object, including validation, hydration of references and event publication.
  • IRepository<T>, ISearchService<T>, IRelationService, IAuthenticationService, IDocumentGenerator, IMailService, IFileSystemService… : ports that the Infrastructure layer implements.
  • Descriptors: declarative descriptions of UI screens (workspaces, domain object browsers, selectors) that the WebUI renders.
  • Application actions: declarative descriptions of what a user can trigger.
  • Workflows, trees, domain object chains, KPIs, activities: business building blocks shared by backend and frontend.
  • Registries and factories: the plug-in points a module uses to register its types.
  • IModuleBootstrapper: the contract a business module implements to plug into the framework.

Infrastructure

The adapters driven by the application: everything that touches a database, a file system or a third-party library. Entity Framework Core contexts for SQL Server and SQLite, generic repositories mapping domain objects to entities with AutoMapper, the search service, relation resolution, JWT token generation, password hashing, Serilog logging, mail, printers, image compression and document storage.

DocumentRendering

A specialised infrastructure project for generating documents. It renders Scriban HTML templates with data loaded from domain objects and converts the result to PDF with PuppeteerSharp.

Adapter

The driving adapter on the server side: ASP.NET Core Web API controllers. Most of them are generic (DomainObjectController<TDomainObject, TSearchResult>, DomainObjectSearchController<…>) and are closed per domain object type at startup.

Bootstrapper

The toolbox of the composition root. It is not a layer: it sits above all of them and only exposes generic helpers (registration of closed generic controllers, route conventions, service registration shortcuts). The actual composition root is the host application, outside this repository, which is why Bootstrapper itself only references Application.

WebUI

The Blazor frontend. A Razor class library built on MudBlazor that renders the descriptors defined in Application and calls the REST API through HTTP gateways. It depends on Application and Domain for the types it displays, but never on Infrastructure.

How a module plugs in#

The framework alone does nothing visible. A business module brings the actual features and plugs in by implementing IModuleBootstrapper (Application) and, for its controllers, IWebApiModuleBootstrapper (Adapter). The bootstrapper declares:

  • the backend and frontend service assemblies to scan,
  • the domain object types and their entity mapping,
  • browser and selector descriptors, constraints, icons and components for the UI,
  • workflows and their context loaders,
  • relations: references, reference lists and parent/child trees,
  • navigation actions, domain object chains and settings,
  • the workspaces (screens) it contributes.

A host application collects the module bootstrappers, registers everything with the helpers from Bootstrapper, configures a database context and serves both the API and the Blazor UI.

Design choices worth knowing#

  • Domain objects and entities are distinct types. A domain object is what the business logic and the UI manipulate. An entity is what EF Core persists. AutoMapper profiles, contributed per module, translate between the two. This keeps the domain free of persistence attributes.
  • Generics everywhere. Services, repositories, search services and controllers are generic over the domain object type. A module rarely writes a controller or a repository; it registers closed generic types.
  • Declarative UI. Screens are described by descriptors and actions in the Application layer, and rendered by generic Blazor components. A module gets a browser, an editor and a page for a new domain object type mostly by configuration.
  • Keys over types across the wire. Actions, constraints, workspaces, relations and settings are identified by string keys declared in Contracts, so the frontend and backend can refer to them without sharing implementation types.

BusinessAppFramework.Contracts

Shared
Layer
Shared, innermost
Depends on
Nothing
Used by
Every other project

Role

Contracts holds the constants that the backend and the frontend must agree on. It has no behaviour and no business type, so it can be referenced from anywhere, including the Blazor client, without dragging in the domain model.

What's inside

  • Keys: ActionKeys, ConstraintKeys, DomainErrorKeys, MessageKeys, SettingsKeys, StringKeys, EnumKeys. String identifiers for actions, filters, errors, translated strings and settings.
  • Aggregate keys: DomainObjectAggregateKeys and DomainObjectSearchResultAggregateKeys derive a stable route key from a domain object type.
  • API routes: the ApiRoutes folder defines the URL segments of the REST API (domain objects, search, trees, workflows, documents, navigation, relationships) and the ApiRoute helper that assembles them.
  • Enums: Language and TimeUnit, with extension methods.
  • KebabStringFormatter: turns type names into kebab-case route segments.
Why it is a separate project

Putting these constants in Domain would force the frontend to reference business types just to build a URL. Keeping them apart also makes the HTTP contract between Adapter and WebUI explicit and easy to find.

BusinessAppFramework.Domain

Domain
Layer
Domain
Depends on
Contracts
Used by
Application, Infrastructure, Adapter, DocumentRendering, WebUI

Role

Domain defines what a business object is in the framework. It contains no persistence, no HTTP and no UI code. Every business module derives its own objects from the types found here.

What's inside

  • DomainObject: the abstract base class of every business object. It carries an Id and audit fields (creation and last modification date, user id and user name), all tagged with SystemPropertyAttribute so the UI can tell them apart from business properties. It also knows how to clone itself and how to enumerate its references.
  • DomainObjectReference and DomainObjectReferenceList: typed links from one domain object to one or many others, identified by a relation key. They hold the target id plus a display value so the UI can show them without an extra round trip.
  • HistoryInfo: the audit information as a value object, shared with persistence entities.
  • LocalizedText: a dictionary of culture to text with fallback resolution, plus its JSON converter.
  • Marker interfaces: IIndexable for objects that have a user-defined order, ISystemObject for objects identified by a system code and protected from deletion, IHasReferenceNumber for objects that carry a human-readable number.
  • IPasswordService: the only service contract in Domain, used for password hashing.
  • UserRolePermissionType and GlobalVariables.
In practice

A module creates a class such as Customer : DomainObject, adds business properties and, for links to other objects, properties of type DomainObjectReference. The rest of the framework (services, repositories, search, UI) works on any such class.

Projectdocs/projects/Application.md

BusinessAppFramework.Application

Application
Layer
Application
Depends on
Domain, Contracts
Used by
Infrastructure, Adapter, DocumentRendering, Bootstrapper, WebUI

Role

Application is the largest project and the center of the framework. It defines the use cases, the ports that the infrastructure implements, and the declarative building blocks that the UI renders. It is shared by the server and the Blazor client.

What's inside

Use cases and services
  • IDomainObjectService<T> / DomainObjectService<T>: create, read, save, delete and validate any domain object, hydrate its references and publish events.
  • WorkflowService, AuthenticationService, CalendarService, LocalizedStringService, ModuleSettingsService, UserSettingsService, ReferenceHydrator.
Ports (interfaces)
  • Persistence and search: IRepository<T>, IIndexableRepository, IStatusRepository, ISearchService<T>, ISearchGateway.
  • Relations: IRelationService, IReferenceResolver, IParentChildRelationResolver, IDomainObjectTypeMap.
  • Technical services: IFileSystemService, IFileSerializationService, IDocumentStorageService, IImageCompressionService, IMailService, IPrintersService, IAuthenticationTokenService, ICurrentUserService, IUserDialogService.
Declarative building blocks
  • Descriptors: WorkspaceDescriptor names the component that renders a screen; DomainObjectBrowserDescriptor describes a searchable list of one domain object type, with its actions and constraints; DomainObjectSelectorDescriptor describes a picker.
  • Actions: ApplicationAction and its variants (HTTP, navigation, file download, document generation, open dialog). The UI shows them as buttons, the backend executes them.
  • Browser/Constraint: a named filter expressed as a LINQ expression over a search result.
  • Workflows: ProcessWorkflow, Step, Transition, Condition, WorkflowContext.
  • Trees: Tree, Branch, Node, NodeSummary for parent/child hierarchies.
  • DomainObjectChains: the navigation chain from one object to its related objects, shown as a breadcrumb.
  • Kpis and Activities: indicators and counters shown on dashboards.
  • Search: SearchRequest, PaginatedSearchRequest, SearchResult, DomainObjectSearchResult.
Extension points
  • IModuleBootstrapper: the contract a business module implements to register everything it contributes.
  • Registry and the registries built on it (settings, reference navigation keys), plus the factories (DomainObjectServiceFactory, WorkflowFactory, TreeFactory, ConstraintFactory, WorkspaceDescriptorFactory and others) that resolve registered items by key or by type.
  • DomainObjectEvents: an in-process event bus with created, saved, deleting and deleted events a module can handle.
  • Mapping/IMappingProfileContributor: how a module provides its AutoMapper profiles.
In practice

Most of a module's backend code is configuration against this project: register domain object types, declare descriptors and constraints, write a few event handlers or a workflow. The generic services do the rest.

BusinessAppFramework.Infrastructure

Infrastructure
Layer
Infrastructure
Depends on
Application, Domain, Contracts
Used by
The host application

Role

Infrastructure implements the ports declared in Application with concrete technologies. It is the only framework project that knows about Entity Framework Core, Serilog, AutoMapper, Magick.NET or JWT.

What's inside

Persistence
  • OtherSideCoreDbContext: the abstract EF Core context every host derives from. It restricts cascade deletes on all foreign keys and registers an EditDistance database function used by fuzzy search.
  • SqlServerSSPIDbContext and SqliteDbContext: ready-made contexts for the two supported providers.
  • IModelBuilderContributor: lets modules add their entity configuration to the model. The framework contributes module settings and user settings itself.
  • ISeedContributor, DbInitializerService, WebDbInitializerService: database creation and seeding at startup.
  • Repositories: Repository<TDomainObject, TEntity> maps domain objects to persistence entities with AutoMapper and performs CRUD. IndexableRepository, StatusRepository, ModuleSettingsRepository and UserSettingsRepository specialise it.
  • Entities: the framework's own entities (module settings, user settings) and the relation entries used to resolve references and parent/child links.
Search and relations
  • SearchService<TSearchResult>: paginated, sorted and constrained search projected directly from the database.
  • RelationService, ReferenceResolver, ParentChildRelationResolver, DomainObjectTypeMap: resolve typed links between domain objects and build trees.
Technical services
  • JwtAuthenticationTokenService and PasswordService for authentication.
  • Logger built on Serilog with a file sink.
  • MailtoMailService, PrintersService, FileSystemDocumentStorageService, JsonFileSerializationService, ImageCompressionService.
  • WorkflowContextLoader: loads the data a workflow needs to evaluate its state.
In practice

A host picks a database context, registers the repositories and services from this project, and adds the module's model builder contributors and seed contributors. Business modules usually do not write infrastructure code beyond entity classes and mapping profiles.

BusinessAppFramework.Adapter

Entry point
Layer
Entry point (server side)
Depends on
Application, Domain, Contracts
Used by
WebUI (for the HTTP contract), the host application

Role

Adapter exposes the application layer as a REST API with ASP.NET Core controllers. It is the server-side door through which the Blazor frontend, or any other client, reaches the framework.

What's inside

  • DomainObjectController<TDomainObject, TSearchResult>: generic create / read / save / delete endpoints for one domain object type. Business errors are returned as a payload rather than as HTTP errors so the UI can display them.
  • DomainObjectSearchController: paginated and constrained search for one domain object type.
  • AuthenticationController: login and token issuance.
  • DocumentGeneratorController: HTML preview and PDF download of generated documents.
  • WorkflowController, TreeController, RelationServiceController, DomainObjectChainController, NavigationController: expose the corresponding application services.
  • ModuleSettingsController and UserSettingsController.
  • IWebApiModuleBootstrapper: the contract a module implements to declare its closed generic controllers and their route keys.
  • Requests and Responses: the few DTOs that are specific to the HTTP layer (login request, authentication response, document responses).
In practice

A module does not write controllers. It lists the closed generic controller types it needs, for example DomainObjectController<Customer, CustomerSearchResult>, and the Bootstrapper project registers them with ASP.NET Core at startup. Routes are built from the segments defined in Contracts.

BusinessAppFramework.DocumentRendering

Infrastructure
Layer
Infrastructure
Depends on
Application, Domain
Used by
The host application

Role

DocumentRendering turns a domain object into a printable document. A module provides an HTML template and a loader that gathers the data; the framework renders the template and produces HTML or PDF.

What's inside

  • HtmlDocumentTemplate and HtmlDocumentTemplateRegistry: a template is a layout resource plus a content resource, both embedded in an assembly. Templates are registered under a document key.
  • IDocumentModelLoader, DocumentModelLoaderFactory, DocumentModelLoaderTypeRegistry: a loader fetches the data a document needs from a domain object id. The registry associates a loader with a document key.
  • HtmlDocumentRenderer: renders the template with Scriban, then drives a headless Chromium through PuppeteerSharp to produce a PDF. A single browser instance is shared and shut down with the process.
  • PdfPageLayout: page size, margins and orientation.
In practice

A module registers a template and a model loader for, say, an invoice. The DocumentGeneratorController in Adapter then serves an HTML preview and a PDF download for any invoice id, and the UI exposes them through document generation application actions.

Projectdocs/projects/Bootstrapper.md

BusinessAppFramework.Bootstrapper

Composition
Layer
Entry point (composition)
Depends on
Application
Used by
The host application

Role

Bootstrapper is a small project of helpers that a host uses to assemble the framework and its modules at startup. It deals with the one thing ASP.NET Core does not do by itself: discovering and routing closed generic controllers.

What's inside

  • ClosedGenericControllerFeatureProvider: adds the closed generic controller types declared by the modules (for example DomainObjectController<Customer, CustomerSearchResult>) to the MVC controller feature.
  • ClosedGenericRouteConvention: gives each of those controllers its route from the module's route key.
  • ServiceRegistrationHelper: registers an implementation together with every generic interface it implements for a given domain object type, in one call.
  • IBootstrapService and IBootstrapConfiguration: the contract the host implements to provide the service collection and basic configuration such as the log file name.
In practice

The host's startup code collects the IModuleBootstrapper and IWebApiModuleBootstrapper instances of every module, feeds the controller descriptions to the feature provider and the convention, and uses the registration helper to wire services, repositories and search services per domain object type.

Projectdocs/projects/WebUI.md

BusinessAppFramework.WebUI

Presentation
Layer
Presentation
Depends on
Adapter, Application, Domain, Contracts
Used by
The host application and the modules' Blazor components

Role

WebUI is a Blazor component library built on MudBlazor. It renders the descriptors, actions and workflows defined in the Application layer and talks to the REST API exposed by Adapter. It contains no page of its own: the host and the modules compose the application from these components.

What's inside

Components
  • Pages: WorkspaceHost and WorkspaceView render the component named by a workspace descriptor. DomainObjectPages provide the default detail page of a domain object with its header, tabs, history, changes popover and chain breadcrumb. SettingsPage and DocumentGeneratorViewerPage cover settings and document preview.
  • Browser: DomainObjectBrowser, the searchable list driven by a DomainObjectBrowserDescriptor, with constraint chips and action buttons.
  • Editor: property editors for a domain object, including reference and reference list fields, inline properties and categories.
  • Selector and Dialog: pickers and dialogs to choose, create or edit domain objects, confirm or display errors.
  • SearchList: templates, pagination and value indicators for search results.
  • Kpi, Workflow, Images, Mail, NavigationMenu, General: cards, workflow display, image upload and viewer, mail dialog, menu, data grids and badges.
Gateways
  • HttpService and the gateways built on it (DomainObjectServiceGateway, DomainObjectSearchGateway, WorkflowServiceGateway, TreeGateway, RelationServiceGateway, DocumentGeneratorGateway, settings and authentication gateways). Each wraps the calls to one controller of the Adapter, using the routes defined in Contracts.
Services and registries
  • ApplicationActionExecutionService: runs an application action from a click, whether it is an HTTP call, a navigation, a download or a dialog.
  • WorkspaceNavigationService, UserDialogService, DomainObjectCreationDialogService, LocalStorageService.
  • Authentication: cookie-based authentication state and a handler that attaches the JWT to API calls.
  • ComponentRegistry, DomainObjectBrowserWorkspaceRegistry, RelationSelectorRegistry, IconFactory: where modules register their components, workspaces, selectors and icons by key.
In practice

A module gets a working browser, detail page and editor for a new domain object type by registering a descriptor, a search list template and an icon. It writes custom Razor components only for screens that go beyond the generic ones.
